# 服务运行诊断

这是 Open Alert 服务自身的诊断，不是新的币价提醒。不会自动测试 Pushover、发送邮件、重放通知或改变用户配额。异常主动推送目前关闭。

## 入口与权限

- 管理员进入“管理 → 服务运行诊断”；每 30 秒刷新，隐藏页面暂停刷新。失败时保留旧数据，但明确标记过期。
- `GET /api/admin/observability`：真实管理员会话必需；普通账户 403，未登录 401。返回队列、来源、计数和异常/恢复记录。
- `GET /api/readiness`：公开最小状态，只返回 `ready / not_ready / unknown`。只有近期巡检、Worker 数据库探测和当前诊断允许时返回 200；故障、等待首次巡检或未知均返回 503。不返回基础设施、用户或故障详情。
- 原 `/api/health` 语义不变；`degraded` 不会被改写为 `healthy`。正常空闲、通知提供方尚无真实发送样本，也可能导致原健康接口受限。诊断面板单独解释哪些需要处理，不能把“未发现需处理的异常”理解为所有外部投递均已验证。

## 采集与恢复

Cloudflare 每分钟的现有 Cron 先修复 alarm，再检查 API 初始化、Worker 数据库及已知邮件健康，最后通过私有 namespace 提交巡检结果。API/邮件检查失败不能阻止最先执行的调度恢复。不会为巡检发送邮件或通知；初始化失败无法确定邮件本身是否故障时，邮件记为未验证。

协调器按 pending 索引读取 queued/sending 数量、到期数量及最早等待/发送占用时间。正常诊断结果复用最多 15 秒，并合并并发读取；数据库故障会使旧缓存失效，失败的队列读取显示未知而不是零。监控 GET 不执行价格评估或投递。

诊断快照每分钟保存一次；异常开启或确认恢复时立即保存。Cloudflare 将最多 50 条最近一天的事件、最近一小时最多 60 个队列采样和巡检心跳写入 DO 的 `monitor:v1`，不增加业务 SQL migration。未解决事件会保留到记录上限；诊断状态不是业务记录的权威来源。Node 使用进程内定时采集和内存事件，退出会等待当前采集结束，不宣称跨进程持久化。

探测过期、实例重启或提供方变成“尚未探测”不能证明恢复，已知异常不会因此被标记恢复。数据库和监控存储不可用本身也会显式显示。Cloudflare 整个应用无法启动时，内部诊断可能无法读取，此时外部就绪探测应失败；不能依靠服务自身在完全停机后发出通知。

## 指标的含义与边界

| 指标 | 定义 |
| --- | --- |
| 评估周期、异常和达预算次数 | 当前协调器实例的实际 tick；达预算不等于规则丢失，剩余规则仍轮转 |
| 行情轮询调用 / 异常 | polling 源的逻辑采集调用及抛错次数；不是逐条物理 HTTP 请求数，也不是 Node WebSocket 断连统计 |
| 投递成功、失败、不确定和重试 | 当前实例已提交的投递结果；不确定不会自动重发，未提交的发送另计 |
| 预留至结果延迟 | outbox 预留时间到本轮结果提交的耗时，不等于手机最终接收时间 |
| P95 | 固定分桶的上界估计，无样本显示“尚无样本”，超过末桶显示大于 30000ms |
| D1 读写行、调用错误和耗时 | 协调器 SQL 适配器收到的 D1 metadata；CAS 正常竞争单列，耗时为适配器调用墙钟时间 |

计数从 `startedAt` 开始，并以 `runId` 区分实例；协调器重启/驱逐会重新计数。**D1 指标不包含边缘 API、原生认证 Drizzle、其他实例或其他项目，不能当作账号总计费量。** 全量 D1/Worker CPU、内存和配额应在 Cloudflare 平台监测中查看。本次不增加付费分析服务，也不宣称实现了账号级账单告警。

## 判定与处置

- `idle_no_active_alerts`：正常待命，不为保持绿色状态而启动无用行情请求。
- `provider_not_checked`：未获得真实投递证据，不自动发送测试消息。
- `queue_delayed`：已到期通知从预留起等待超过一分钟，检查提供方、配额和积压；不要手工重放不确定事件。
- `delivery_stuck`：sending 占用超过一分钟，检查租约、实例重启和恢复记录。
- `cron_overdue`：超过三分钟没有巡检心跳，检查 Cron、Worker 和数据库；首次启动有等待首次巡检的状态。
- API、邮件、行情或 SQL 错误：结合组件安全代码和最近成功时间排查。只有确认恢复才关闭事件，不能通过清库、清锁或改绿 UI 掩盖问题。

## 日志与外部探测

Wrangler 启用 Workers Logs，但关闭自动 invocation 请求日志；自定义日志只记录安全状态、聚合计数和时间，不记录邮箱、用户 ID、价格规则、SQL 参数、Cookie 或密钥。

- `open_alert_observation`：周期性观测；计数按 runId 解释，不能跨实例直接相加作为完整账单。
- `open_alert_incident`：`opened / resolved` 转换。按 component 和 code 排查，不需要查看业务用户数据。

配置依据：[Cloudflare Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)、[D1 metadata](https://developers.cloudflare.com/d1/worker-api/return-object/)。日志保留与额度由实际平台套餐决定。

仓库提供一次性外部探测命令：

```sh
npm run monitor:check -- https://cryptotool.bar
```

它只访问公开就绪接口：ready 退出 0，503、超时、无效响应和连接失败退出非零。**没有自动创建定时任务或通知订阅。** 若需要停机时主动提醒，应在独立于本 Worker 的监控服务/主机定时调用，再连接经确认的通知渠道；不要把唯一外部探测也放进被监控应用自己的 Cron。

## 验证边界

本地用故障注入验证异常打开、去重、恢复、探测过期不假恢复、持久化重建、存储故障、权限与响应隐私；真实 workerd 验证巡检不发送、不抓取价格、不启动空闲 alarm。包含 20000 条已完成历史的 D1 用例要求监控队列查询不扫描整份历史。UI 验证桌面/手机、中英文、旧数据标记和恢复记录。生产只做只读诊断及日志核对，不人为制造生产故障，不发送真实测试邮件或推送。
