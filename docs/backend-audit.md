# 后端检查：配置与真实行为是否一致

> 后续状态（2026-10-19）：本文保留 `5874f03` 审查时的原始发现。本地已实现第一轮修复和读取优化，见 [优化记录](backend-optimizations.md)；该报告是历史审查快照，实际线上修复状态以发布记录为准。

日期：2026-10-18 至 2026-10-19。基线：`5874f03`。本次检查覆盖认证/限流、启动降级、API 到协调器唤醒、双运行时、行情目录/报价、SQL 租约/CAS、Outbox 和通知边界。**检查发现问题，不代表已修复；此次没有修改生产逻辑、提交或部署。**

## 发现

### [P1] 首次唤醒失败被吞掉，可能显示已开启但后台没有运行

- 位置：`src/api/index.ts:51`、`src/api/index.ts:177`；`src/runtime/cloudflare.ts:52`、`src/runtime/cloudflare.ts:119`。
- 触发条件：DO 原先空闲、没有 alarm；规则/监控设置已经提交到 D1，但随后 `/wake` 在持久化 alarm 前失败。
- 实际行为：API 的 `d.wake().catch(()=>{})` 吞掉异常，仍返回成功。DO 既无 alarm，也无常驻或独立 fallback；关闭浏览器后可能持续不评估规则，直到下一次 `/snapshot`（状态/健康请求）等操作修复。
- 本地证据：真实 Hono、Better Auth 会话和 SQLite 仓储，已存在有效规则与通知渠道；将 wake 端口注入为抛错。设置接口仍 HTTP 200、数据库 `enabled=true`、仅唤醒一次，返回体没有失败或待确认标识。首次无 alarm 时无法自行启动的结论来自 DO 与运行配置的交叉检查，不冒充线上故障复现。
- 建议：最小补丁为有界幂等重试 + 显式激活待确认协议；已提交的设置不能靠通用 5xx 假装回滚。若要真正保证无人打开网页时自恢复，需要独立重试驱动（例如定时补偿或可靠消息消费）；只写一条数据库记录而无人消费不够。
- 现有文档已提到“丢失唤醒依赖后续 status 修复”，但 API 仍隐瞒失败；这是可靠性缺口，不是已具备后台自恢复。

### [P2] 只修了会话读取，其他认证路径仍能落回一小时 60 次

- 位置：`src/auth/options.ts:50`，特别是 `src/auth/options.ts:62`。
- 根因：全局 `window=3600,max=60` 仍存在；当前安装版本的 `'*'` 不匹配含 `/` 的路径。显式 `/get-session` 已修复，但 `/sign-out` 等未单独覆盖的路径仍走全局值。并非所有端点都是小时窗口：库的特殊登录规则与显式 OTP 规则还会覆盖部分路径。
- 本地证据：原生真实认证处理器先完成 60 次 sign-out；只模拟外层自定义一分钟窗口过期，保留原生路径计数；第 61 次实际返回 429、`Retry-After: 3600`，同时 get-session 返回 200。无生产请求。
- 风险：共享出口用户、反复登录退出时可能仍被锁近一小时；只看 get-session 回归会漏掉。
- 建议：确认安装版本的真实路径匹配，并补所有开放路径的请求窗口测试；长期将应用 OTP 小时计数与库原生限流存储/清理策略拆开，避免为了保留记录而改变默认请求限制。不要直接把全局窗口缩短后误删 OTP 小时计数。

### [P2] 启动失败伪装为登录能力已正常读取且未配置

- 位置：`src/runtime/common.ts:28`；调用点 `src/runtime/cloudflare.ts:64`；UI 消费点 `web/pages/Login.tsx:57`、`web/pages/Login.tsx:165`。
- 触发条件：配置、数据库/迁移状态、邮件 readiness 等导致应用初始化失败；已有前端或跨 Worker 实例的登录页请求能力接口。
- 实际行为：`unavailableApi('/api/auth-capabilities')` 返回 HTTP 200、`ok:true`、`google:false,emailOtp:false,registration:'closed'`。前端接受为真实配置，禁用邮件输入、隐藏 Google，也不进入 `capError` 的重试分支。
- 本地证据：直接运行真实 fallback，返回的状态与字段如上。另用构建后的真实 Login 页面做浏览器对照：相同字段的成功响应没有重试按钮；503 错误响应有重试按钮。
- 风险：临时服务问题被错误归因于管理员没配置，服务恢复后页面也不主动重新读取能力。若 session 同时失败，则先进入 App 的会话错误界面，并不总会看到此登录页症状。
- 建议：能力未知应返回可重试的 503/error，和“已确认某登录方式关闭”区分开。

### [P3] 配置宣称租约 15 秒，真正持久化的是 40 秒

- 位置：`src/config.ts:10`、`src/scheduler/index.ts:38`。
- 实际行为：`RUNTIME_POLICY.leaseMs=15000`，但调度器默认使用 `options.leaseMs ?? 40000`；运行时没有传入配置值。
- 本地证据：实际 scheduler tick 后读取 SQL `scheduler_lease.expires_at`，相对同一时钟为 40000ms，配置仍是 15000ms。
- 风险：故障接管预期与调参对象不一致。**不能据此认定 40 秒本身错误**；当前发送 drain 预算 25 秒，直接改成 15 秒可能破坏租约安全余量。
- 建议：先确定覆盖网络/投递预算的租约，再只保留一个实际生效的策略来源，并测试预算关系。

## 已检查且不应误报的问题

- TradingView 是独立图表，不是告警引擎的数据输入；此次未替换或修改组件。
- 行情目录与动态价格分开；目录流在 Worker 不被重复 JSON 解析，普通前端轮询不自动反复抓取全目录。
- 市场源有超时、退避、行情时间戳约束及旧实例退休保护；单个市场范围异常不应伪装为正常价格。
- 通知结果不明不自动重发，是对外部非事务性提供方的安全策略，并非“重试漏写”。
- SQL Outbox、generation/CAS、加密渠道凭据、租户隔离和 fencing 已存在，不需要为这些能力再造一套内存队列。
- Cloudflare 一轮只预留/发送一次是现有成本/吞吐边界，不等于“100 条规则同时达到阈值也能 5 秒内通知”。此项应明确产品承诺，不能靠 UI 动画遮盖。

## 架构结论

当前架构对自托管、小规模多用户告警是可理解的：模块化单体 + 单协调器 + SQL Outbox，避免了不必要的基础设施。优先问题是**状态真实性与故障恢复**，而不是缺少微服务。先修 P1，再补认证边界与降级协议，最后统一配置。
